# Person B Architecture Compliance Review

## 1. Overview & Completed Items
The current implementation successfully delivers the complete Person B scope for the AEGIS demo. The dashboard is fully functional, visually reflects the "Understand → Reason → Plan" cycle, and successfully orchestrates the 30-second judge demo flow from a single button click.

**Completed Items:**
- **UI Structure & Dashboard**: Built the exact layout specified in `gameplan.md`.
- **Live Drone Telemetry**: Integrated dynamic 2D radar visualization with trajectory mapping.
- **Mission Dependency Graph**: Reactive dependency tree (GPS → IMU → Position Estimation → Navigation) using `@xyflow/react`.
- **Agent Trace Panel**: Scrolling timeline of LLM investigation steps and tool calls.
- **Evidence & Hypotheses Panels**: Visual rendering of agent evidence and confidence-weighted hypotheses.
- **Response Options UI**: Candidate actions with risk classification and highlighting of recommended actions.
- **Governance Gate**: Human-in-the-loop authorization UI for high-risk actions.
- **Demo Flow**: Executable end-to-end incident scenario (Fault → Agent Investigation → Policy Gate → Execute → Verify Fail → Replan → Recover).
- **Data Contracts**: Fully typed `types/simulator.ts` matching the exact JSON payloads from `PERSON_A_BUILD_PROMPT.md`.

---

## 2. Architecture Compliance & Violations

### Frontend / Backend Separation
Because Person A's backend was not available during implementation, the **entire simulation and agent logic is currently mocked inside `SimulatorContext.tsx`**. While this enables the demo to run flawlessly in isolation, it violates the final architecture.

### Simulator Placement
- **Violation**: The AEGIS Core logic (Trust evaluation, Risk assessment, Evidence generation, Candidate action generation, Policy evaluation, and Verification) is currently hardcoded in the frontend's `SimulatorContext.tsx`. 
- **Architectural Truth**: According to `gameplan.md`, Person A owns the "Decision Core" (Evidence, Trust, Risk, Policy, Simulation, Execution, Verification).

### Drone Simulator Ownership
- **Compliance**: According to `gameplan.md`, Person B *is* responsible for the "Drone Simulator (Telemetry, GPS, IMU, Fault Injection)".
- **Current State**: The drone kinematics (movement tick) and fault injection (`gps_trust: 0.31`) are managed in React state. 

---

## 3. Required Integration Changes (Next Steps)

To transition this implementation into the final architecture, the frontend needs to stop generating state and start consuming it from the FastAPI backend.

### What should remain in the Frontend (Person B):
1. **Drone Kinematics & Fault Injection Trigger**: The frontend can still trigger the fault (`POST /api/v1/scenario/gps-integrity`), but the backend must maintain the official state.
2. **UI & Visualization**: All components (`DroneTelemetry`, `MissionGraph`, `AgentPanels`, `SimulationActionPanels`) are perfectly structured to consume props/context. 
3. **Data Contracts**: The TypeScript interfaces in `types/simulator.ts` are correct and should be kept as the source of truth for the UI.

### What must move to the Backend (Person A):
1. **Agent Orchestration**: `SimulatorContext.tsx` currently uses `setTimeout` to mimic the agent thinking. This must be replaced by the real LLM runtime in Person A's backend.
2. **Core Logic**: Trust degradation, risk calculation, hypothesis generation, and candidate action simulation must be generated by the FastAPI backend.
3. **Verification Logic**: The deliberate verification failure (for the demo) must be managed by Person A's `verify_action()` tool.

### API Contracts Person A Needs to Implement:
For Person B to hook up the UI, Person A must expose the following stable APIs:

1. **`GET /api/v1/state`**
   - **Returns**: `DroneState` (time, position, velocity, navigation_mode, gps_trust, imu_trust, mission_progress, mission_status, mission_risk).
   - **Person B Action**: Poll this endpoint every 1000ms to update the Telemetry and Graph UI.

2. **`GET /api/v1/agent/events`** (or WebSocket)
   - **Returns**: Array of `AgentEvent`, `Evidence`, `Hypotheses`, `CandidateAction`, and `VerificationResult`.
   - **Person B Action**: Consume this to populate the Agent Trace, Evidence, and Response Options panels.

3. **`POST /api/v1/scenario/gps-integrity`**
   - **Action**: Triggers the GPS fault in the backend simulator.
   - **Person B Action**: Tied to the "Run Incident" button.

4. **`POST /api/v1/agent/authorize`**
   - **Payload**: `{ action_id: "switch_inertial", approved: true/false }`
   - **Person B Action**: Tied to the "APPROVE" / "REJECT" buttons in the Authorization panel.

## 4. Final Recommendation
Do not rewrite the frontend code right now. The UI components are fully isolated and clean. 
When Person A completes the FastAPI backend, the only required change for Person B is to rewrite the functions inside `SimulatorContext.tsx` to perform `fetch()` calls to `http://localhost:8000/api/v1/...` instead of updating local React state.
